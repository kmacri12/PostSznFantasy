# Protecting sign-in accounts: Supabase Auth and the backup (#215)

Checked 2026-10-31 against the pages linked below. Question: if the Supabase project is paused past its window or deleted, how do players keep their accounts, given that `fantasy.users.supabase_uid` is the Supabase user id and the backup (`scripts/backup-db.sh`) dumps only `public`, `nfl` and `fantasy`?

## Findings

1. **Free projects are not backed up by Supabase.** Daily backups exist only for Pro, Team and Enterprise (Pro keeps 7 days). Free projects are told to export with `supabase db dump` and keep copies off-site. Deleting a project removes its backups. [Database backups](https://supabase.com/docs/guides/platform/backups) (the page says nothing about backups of paused projects).
2. **Pause rules.** A Free project is paused when it lacks "sufficient user database activity over the past week"; a few database requests a day is usually enough. Owners get a warning email about a week earlier. [Project pausing](https://supabase.com/docs/guides/platform/free-project-pausing).
3. **Restore window: the docs disagree.** The pausing page says a paused project can be restored for **up to 1 year**. The troubleshooting article on pausing Pro projects links a related article titled "Restore a project after 90 days of pause" and does not state a window itself ([Pausing Pro projects](https://supabase.com/docs/guides/troubleshooting/pausing-pro-projects-vNL-2a)). The existing runbook already treats this as unknown; plan on the shorter figure.
4. **Auth data is in the database, in the `auth` schema** (`auth.users`, `auth.identities`). The user guide only says a user "has a user ID, stored in the Auth schema" and a user can have several identities (email, phone, OAuth, SAML) ([Users](https://supabase.com/docs/guides/auth/users)). Passwords, when used, live in `auth.users.encrypted_password` ([Auth0 migration guide](https://supabase.com/docs/guides/platform/migrating-to-supabase/auth0)). The Passwords guide does not name the algorithm.
5. **Supabase's CLI dump has no schema filter.** `supabase db dump --data-only` would carry `auth` data, but the page does not say so explicitly and tells you to confirm on your own project; the restore steps load roles, schema, then data with `session_replication_role = replica` ([Backup and restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)). Supabase's dashboard-restore page says a new project already has `auth` and `storage` objects, so "already exists" errors are expected, and Auth settings and API keys are not in the database and must be recreated ([Restore dashboard backup](https://supabase.com/docs/guides/platform/migrating-within-supabase/dashboard-restore)). I found no official guide for loading `auth.users` and `auth.identities` into a new hosted project while keeping ids; only community posts. A raw `pg_dump` of Supabase internals is documented as causing permission errors ([self-hosting restore](https://supabase.com/docs/guides/self-hosting/restore-from-platform.md)).
6. **A supported way to recreate a user with the same id exists.** The Auth server's admin create-user handler accepts `id` (must parse as a UUID; nil is rejected), `email`, `email_confirm`, `password_hash`, `user_metadata` and `app_metadata` ([supabase/auth `admin.go`](https://raw.githubusercontent.com/supabase/auth/master/internal/api/admin.go), read from source because the JS reference page lists only a few fields). The Auth0 guide confirms: "You can pass a custom `id`" if it is a UUID, and `password_hash` takes bcrypt or Argon2. Docs gap: the JS `createUser` reference page does not mention `id` or `password_hash`; rely on the Auth server source and test on a scratch project before trusting it.
7. **Identity linking is by verified email.** Auth "automatically links identities with the same email address to a single user", requires unique emails, and calls linking to an unverified address "an insecure practice" (pre-account takeover). When a new identity links, other unconfirmed identities on the user are removed. The page does not describe magic links, and it does not say whether Google emails are marked verified ([Identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking), [Google login](https://supabase.com/docs/guides/auth/social-login/auth-google)).
8. **Magic link signs a new user up by default** (`shouldCreateUser: false` stops that), is single use, and expires after 1 hour; the page does not say whether it marks the email confirmed ([Passwordless](https://supabase.com/docs/guides/auth/auth-email-passwordless)).
9. **This app never uses passwords.** Sign-in is Google OAuth or magic link, so there is nothing secret in `auth.users` that the app needs to survive a rebuild: id, email, confirmed flag and providers are enough.

## Not verified (treat as open)

- Whether a user created by the admin API with `email_confirm: true` and no identity row then gets a Google identity auto-linked on first Google sign-in. Identity linking says it should (same verified email); confirm on a scratch project before launch.
- Whether Google sign-ins always arrive with a verified email in Supabase.
- Exact restore window (item 3).

## What the app already has

`fantasy.users` stores `supabase_uid` (unique), `email` (unique, nullable) and `username`, and is in every backup. `POST /api/auth/login` upserts by `supabase_uid` and returns 409 if the email already belongs to another row. So the facts needed to recreate an account (id and email) already ship in the encrypted dump, without a password hash.

## Options compared

| | Recovery time | Security | Complexity | Cost | Fit with Google + magic link |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. Stay active all off-season** | None while it works; if the project is lost anyway, everyone re-registers and old leagues are orphaned | Nothing new stored | Documentation plus a guard | $0 (weekly keep-alive) | Perfect, but a single point of failure (account suspended, project deleted by mistake, pause window lapsed) |
| **2a. Dump the `auth` schema into the backup** | Hours, manual, fragile (items 4, 5 above) | Backup then holds `encrypted_password` hashes, tokens and session data; gpg only | High: Supabase-internal roles, triggers and ownership break a raw `pg_dump` | $0 | Works, but carries data the app never uses |
| **2b. Recreate users from `fantasy.users` with the admin API, same id** | Minutes: one script after the restore | The script needs the service-role key, run by the owner locally only; no hashes anywhere; `email_confirm: true` is the owner vouching for emails the app already holds | Low: one script, no schema change, no migration | $0 | Good: magic link works at once, Google links by verified email (verify, see open items) |
| **3. Link by email on first sign-in** | Instant, no owner action | Highest risk: any new Supabase id presenting a matching email would take over the old row; safe only with a verified email, and the app cannot see verification in a JWT for every provider | Medium: change to `/api/auth/login`, new rules and tests | $0 | Fits, but it moves account-identity trust into the app; it would also make a Supabase sign-in problem look like a takeover |

Verdict: **1 as the baseline and 2b as the recovery path.** 2b turns "everyone signs up again" into one command, with no hashes stored and no change to the live sign-in path. 2a is rejected (hashes in backups, unsupported restore). 3 is rejected as the default; it stays available as a break-glass manual SQL step only if ids cannot be reused.
